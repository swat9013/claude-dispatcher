# ADR 0028: ある種類の一覧が致命的に失敗しても、ほかの種類の一覧を読み終わるまで待つ

- Status: Accepted
- Date: 2026-10-26
- #459 で決めた振る舞いの理由を記録する (振る舞いは変えない)

## Context

tick の snapshot を作るとき、loop は trigger に現れる種類 (issue・CL) の open な一覧を並べて読む (system.md §7 の手順 3。`places.OpenItems`)。issue 置き場と CL 置き場が別のサービスでも、tick が待つのを遅いほうの一覧だけにするため。

ある種類の一覧が致命的に失敗すると、その tick は snapshot を作らず、何も起動しない (読めない一覧で候補を決めない)。このとき、ほかの種類の読み出しが終わっていないことがある。例えば Jira + GitLab の構成で acli の認証が切れ、GitLab の open な merge request の一覧が 15 秒を超える tick。

失敗した時点で返せば、tick の error の行は早く出る。待てば、ほかの種類の読み出しが終わるまで出ない (上限は CLI 1 回の上限 120 秒 × その一覧が撃つ回数)。

## Decision

**ある種類の一覧が致命的に失敗しても、ほかの種類の読み出しを止めず、すべて読み終わるのを待ってから、種類の順で先の失敗を 1 つ返す** (system.md §7 の手順 3)。

- 読み出しを途中で止めるには、止める口が、issue 置き場の部品・CL 置き場の部品 (コードでは 2 つを束ねる `places.Store`) と、部品が撃つ CLI の Runner の seam (system.md §13) のすべてに要る。止めても、起動した CLI は捨てた結果のために走り続けうる
- 止めて得るのは、致命的な失敗の tick で error の行が出るまでの遅れが縮むことだけ。その tick は何も起動しないので、待っても失う作業は無い

## Consequences

### 良い影響

- issue 置き場の部品・CL 置き場の部品と Runner の seam が、読み出しを止める経路を持たずに済む
- 返す失敗は読み終わった順に依らず種類の順で決まるので、同じ入力なら同じ失敗が返る

### 悪い影響 / 制約

- 致命的な失敗の tick で、tick の error の行が出るまで、ほかの種類の読み出しの分だけ遅れる
- その tick でも、ほかの種類の遅い一覧の行 (`slow_listing`。formats.md §4・§6) が tick の error の行より前に出うる。試運転と `doctor` でも、stderr に遅い一覧の行が増えうる
- GitLab の CL の一覧が撃つ conflict の計算し直しの要求も、失敗する tick で撃たれる (観測の結果を変えない補助の要求。system.md §13)

## Alternatives considered

### 失敗した時点で返し、残りの読み出しを捨てるか取り消す

- 却下理由: 取り消すには、止める口を issue 置き場の部品・CL 置き場の部品と Runner の seam のすべてに足し、捨てた読み出しの後始末も要る。捨てるだけ (取り消さない) なら、起動した CLI は捨てた結果のために走り続けうる。どちらでも縮むのは、何も起動しない tick の error の行が出るまでの遅れだけ
